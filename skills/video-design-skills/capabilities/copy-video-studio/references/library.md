# 文案知识库

> 用户攒的文案 + 他满意的新文案，沉下来当参考。
> 但**文案会过期**——不是文案本身过期，是平台规则变了，照旧的写法会被限流。

## 1. 目录

```text
~/.video-design/library/
├── index.json          # 条目索引：id / 类型 / 平台 / 标签 / 日期 / 状态 / 复审日期
├── entries/
│   ├── 001.md          # 原稿 + 好在哪 + 可复用句式
│   └── 002.md
├── rules-log.json      # 平台规则变更记录
└── style.md            # 从库里提炼的风格特征
```

## 2. 入库：只存「满意的」

- 用户说「这条不错」「这条发出去还行」→ 存。
- 用户没说满意 → **不存**。自动存等于把废稿也当教材。
- 存的时候必须填「好在哪」，一句话就行：钩子狠 / 接地气 / 节奏快 / 结尾收得住。
- 用户说不清就自己总结，让他点头。

条目格式见 `assets/library-entry.md`。

## 3. 状态：每条都有生命周期

| 状态 | 意思 | 检索时 |
|---|---|---|
| `active` | 可用 | 正常引用 |
| `stale` | 可能过期，等复审 | **不引用**，但生成前提醒用户 |
| `retired` | 停用 | 不引用 |

一条文案从入库到退役：

```text
active ──(平台规则收紧)──> stale ──(复审通过)──> active
                              └──(复审不过)──> retired
```

## 4. 规则变了怎么办（核心）

平台收紧不是一条文案的问题，是**所有同类文案都可能中招**。

所以收到「平台最近管得严」这类信息时：

1. 记一条规则变更到 `rules-log.json`：
   ```json
   {"date": "2026-11-09", "platform": "抖音", "change": "招聘类限流收紧", "tags": ["择业", "招人"]}
   ```
2. 把命中这些标签的条目批量标 `stale`。
3. 生成文案时，如果检索到 `stale` 条目，**先提醒**：
   > 「你库里那几条是旧规则下写的，现在这类内容管得紧，我按新规则改了说法，不照搬。」
4. 复审：改写成新版 → 旧版标 `retired`，新版入库为 `active`。

**绝不做的**：照着 stale 的条目直接套。套出来就是被限流的那篇。

## 5. 检索：只取最像的 2–3 条

生成前按「类型 + 平台 + 标签」查索引，取最多 3 条 `active`。

不读全库——攒一百条全读就是几万字，上下文直接爆。

检索顺序：

1. 同类型 + 同平台
2. 同类型，平台不同（降一档）
3. 标签最匹配的

## 6. 提炼：攒够再抽风格

条目到 5 条以上，抽一份 `style.md`：

- 常用开头句式
- 句子长度区间
- 爱用的词、绝不用的词
- 结尾习惯

`style.md` 也会过期——每次规则变更后重抽一遍。

## 6.5 发布后回写（关键）

写出来什么样，和发出去什么结果，是两回事。用户回来说结果时，记一笔：

```bash
library.py result --id 001 --result throttled --note "发出去没推"
library.py result --id 002 --result hit --note "播放 30w"
```

| 结果 | 处理 |
|---|---|
| `throttled` | 标 stale，先复审；同类内容生成前提醒 |
| `normal` | 记录，不改状态 |
| `hit` | 记录，以后检索**优先用这条** |

**为什么不自动判断**：平台数据在用户后台，模型拿不到。必须用户回来说，或他贴数据截图。

这条回路不建，知识库只记得「写出来什么样」，记不住「发出去什么结果」。

## 7. 隐私

品牌名、价格、客户信息都在里面，**只存本地，不上传**，不进任何云端知识库。

## 8. 自检

- [ ] 只存了用户确认满意的
- [ ] 每条都有「好在哪」
- [ ] 每条有入库日期和状态
- [ ] 规则变更后，相关条目已标 stale
- [ ] 生成时没直接套 stale 条目
